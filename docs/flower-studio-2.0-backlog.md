# Flower Studio 2.0 后续产品与工程 Backlog

状态：2026-11-18 基于第一阶段 WMS 迁移计划整理。Sprint 2 已进入开发分发；本文主要记录 Sprint 3 及后续工作，不替代每个 Sprint 开始前的功能规格、技术设计和测试计划。

## 规划原则

1. 第一阶段结束前，V2 必须能够独立替代 V1 WMS；CMS、CRM 和小程序不作为第一阶段关闭条件。
2. 未经确认的新增能力不混入迁移 Sprint；优先迁移 V1 已验证功能和已经确认的 V2 业务规则。
3. 正常流程尽量自动推进，人工确认集中在降级、替代、差异、短缺、退款和异常恢复等例外场景。
4. 每个 Sprint 必须具备可独立开发、测试和验收的边界，并保留 V1/V2 对照证据。
5. DSH 负责实现和第一层自动化验证；Codex 负责范围审查、关键规则复核及正式工作区独立验收。

## 当前批次：Sprint 2 — WMS 运营保障

目标：补齐 V2 WMS 上线后的经营观察、问题定位和日常保障能力。

范围：

- WMS 经营仪表盘及待办；
- V1 既有 WMS 报表迁移；
- 采购、库存、效期、损耗、成本和低毛利报表；
- 试运营检查；
- 数据质量中心；
- 系统健康检查；
- V2 审计事件查询。

关闭条件：上线运营和排错能力不需要返回 V1；报表口径能追溯到明细；检查项具有明确状态和处理入口。

## Sprint 3 — V2 WMS 上线与切换

### 目标

完成第一阶段最终收口，使 V2 可以正式替代 V1 WMS。

### 工作项

- 建立完整 V1→V2 WMS 回归清单并逐项关闭；
- 覆盖订单、采购、库存、制作、损耗、退款、配送和成本的端到端回归；
- 验证并发预留、批次锁定和关键查询性能；
- 验证空库部署、增量迁移、seed、备份、恢复和回滚；
- 完成真实门店多角色试用；
- 修复试用中发现的阻断问题；
- 确认 V1 WMS 兼容入口、短期回退方案和最终切换步骤；
- 形成可发布版本及上线验收记录。

### 验收标准

- 正常 WMS 操作无需进入 V1；
- 第一阶段差距矩阵没有未确认的阻断项；
- 自动化回归、构建、迁移、恢复演练和真实用户验收通过；
- V2 保留 V1 的整体后台样式、信息密度和主要操作习惯；
- V1 WMS 仅作为受控的短期回退版本保留。

## Sprint 4 — 打样优化与样品转商品

### 目标

将已经确认的样品花材搭配流程接入统一物料、库存、配方和 SKU 模型。

### 工作项

- 样品方案创建、编辑、复制和版本记录；
- 按现货库存辅助推荐可用花材，但不自动替代人工确认；
- 样品领用、实际用量、损耗和拆解退库；
- 样品成本与目标售价测算；
- 一份样品生成多个 SKU；
- 多份样品生成同一商品下的多个 SKU；
- 调整数量、花材、包材颜色后生成 SKU 变体；
- 商品页面选择多个 SKU、分别定价并设置默认 SKU；
- 样品复用、转化率和成本偏差报表。

### 验收标准

- 打样不绕过正式库存流水和成本规则；
- 正常领用流程操作足够轻量；
- 样品与商品、SKU、配方之间的来源关系可追溯；
- 同一商品和同一样品的多 SKU 关系符合已确认规则。

## Sprint 5 — CMS 商品内容与营销迁移

### 目标

让 CMS 完全使用 V2 商品、SKU 和库存口径，不再依赖 V1 业务模型。

### 工作项

- 商品内容、图片、卖点、运营备注和富文本；
- 商品分类树、排序和多分类关联；
- Banner、推荐位、场景入口和营销内容；
- 配送设置、时段、容量和预订规则；
- 商品、SKU、配方和分类搜索选择器；
- 小程序商品卡片预览及图片失败提示；
- 上架完整性检查和风险提示；
- 商品定价模拟、毛利预估和建议售价；
- 商品决策建议沿用 V1 规则，仅适配 V2 数据。

### 验收标准

- CMS 所有写入进入 V2 模型；
- 上架检查使用 V2 配方和库存能力；
- 图片、内容和营销配置不影响 WMS 交易稳定性；
- V1 CMS 正常操作均有 V2 入口或确认过的替代方案。

## Sprint 6 — CRM 与客户运营迁移

### 目标

将客户、收花人、礼赠历史和复购提醒接入 V2 订单数据。

### 工作项

- CRM 总览和客户指标；
- 客户列表、搜索、筛选和分页；
- 客户详情、收花人、订单和礼赠历史；
- 复购提醒及状态流转；
- 订单保存客户与收花人快照；
- 礼赠推荐沿用 V1 规则，仅适配 V2 商品和库存；
- 提醒服务失败不得阻断下单和履约。

### 验收标准

- CRM 查询和操作不再依赖 V1 订单；
- 历史订单展示不受客户资料后续修改影响；
- 推荐和提醒属于辅助能力，不成为交易流程卡点。

## Sprint 7 — 微信小程序接入 V2

### 目标

将小程序商品浏览、购物车、下单、支付和订单进度完整切换至 V2。

### 工作项

- 微信登录、用户资料和头像；
- 商品列表、详情、筛选、排序和分页；
- 分类、Banner、推荐位、场景入口和首页聚合；
- 购物车增删改及结算前校验；
- SKU 选择和 V2 可售量检查；
- 小程序创建订单及订单列表；
- 待支付取消、确认收货和配送进度；
- 常用收花人 CRUD 和历史快照；
- 测试环境 Mock 支付；
- 正式微信支付和幂等回调；
- 图片 URL 和 OSS 安全输出。

### 验收标准

- 小程序 API 全部使用 V2 身份、商品、库存和订单模型；
- Mock 支付只在测试环境启用；
- 支付成功、重复回调、超时关闭和退款具有可重复验证的状态结果；
- 后台人工下单入口继续保留。

## 后续候选能力

以下能力不自动进入上述 Sprint，需经过真实门店试用或单独业务确认后排期：

- 丝带、胶带等整卷耗材的逐卷状态管理；
- 多门店正式运营和租户自助管理；
- 高级需求预测和自动采购建议；
- 自动替换物料决策；
- 重新训练或调整商品决策、礼赠推荐算法；
- 新的营销玩法和会员体系；
- 超出当前单店运营规模的复杂审批流。

## 每个 Sprint 的进入条件

- 业务范围和明确不做事项已经确认；
- User Story 或功能规格具备可测试验收条件；
- 数据模型变更经过审查；
- 工作包可以拆成互不覆盖的文件和服务边界；
- 测试数据、账号、环境和依赖已准备；
- 上一个依赖 Sprint 已通过独立验收。

## 每个 Sprint 的完成条件

- 功能入口、数据读写、权限、异常反馈和审计符合范围；
- TypeScript、Lint、单元、数据库集成、构建和适用的浏览器测试通过；
- 未覆盖用户现有改动，未修改范围外模块；
- 变更文件和测试证据完整；
- Codex 在正式工作目录完成独立验收；
- 用户确认真实业务流程没有新增不必要操作卡点。
