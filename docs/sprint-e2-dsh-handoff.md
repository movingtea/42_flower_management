交接日期为 2026-11-10。基线为 `CMS_and_WMS` 仓库 `dev` 上的 `9112ed3`（Sprint E1 Done），交接盘点时工作树干净。E2 沿用「V2 重构」中的六项范围：staging、SHA 镜像部署、自动备份、恢复演练、迁移前后验证、回滚及发布记录。下面的工作包编号和执行顺序用于交接。

DSH 的执行权限限于工作区和经授权的非生产目标。现有 [生产 workflow](../.github/workflows/deploy.yml) 在 push 到 `master` 时触发 ACR 推送和远程部署。工作包应通过独立入口演练。生产触发条件、运行中数据库容器及其卷、凭据和云端设置由维护者管理。V1/V2 继续按 ADR-001、002 分库、分连接与迁移历史，V1 退役及生产恢复由项目用户审批。

## E2.1 · 建立 staging 和真实镜像基线

范围为新增 `deploy/staging/` 的 Compose、示例配置和文档。复用 [Dockerfile](../Dockerfile)、[Compose 示例](../docker-compose.example.yml) 和 `deploy/rehearsal` 的资源隔离方式。若真实构建失败，先记录实际错误，仅在证据指向构建问题时提议扩大到 Dockerfile 或应用构建配置。

- 使用当前提交构建实际应用镜像，记录源码 SHA、构建命令、架构和本地 image ID。远程 staging 使用仓库中的 immutable digest 并记录它与源码 SHA 的对应关系。保留构建日志和可复查入口。实际构建失败时单列阻塞。
- staging 使用独立项目、容器、端口、网络、卷、V1/V2 库和合成数据。外部服务使用隔离测试配置。启动前验证部署目标，持久化试验只重建隔离数据库容器，并确认原有测试数据保留。
- 验收需要实际镜像启动、双库迁移状态、web 健康、登录与 V2 入口冒烟、cron 状态和隔离资源清单。远程部署须有真实 registry push/pull 与 staging 执行证据。本机结果单独标为本机验证。

## E2.2 · SHA 部署与失败停止

范围为 `deploy/staging/` 的部署及预检入口。待本地验证后，可提议新增独立的 staging workflow，写入前明确其触发条件、镜像库、目标主机和最小权限。对照 [现有生产部署](../.github/workflows/deploy.yml)、[应用入口](../flower-wms-system/docker-entrypoint.sh) 和 [V2 数据库目标检查](../flower-wms-system/scripts/check-v2-database-target.mjs)。

- 部署显式接收目标 SHA 或 digest，解析后用同一镜像启动 web 和 cron，记录部署前实际运行的镜像和回滚候选。串行化同一目标上的发布。目标、镜像或数据库预检失败时，在替换应用前退出。
- 接入 E2.4 的迁移和校验。每次发布由一个入口负责迁移，避免独立迁移与 web entrypoint 重复执行。验证迁移完成且 web 健康后再启动 cron 并确认有效运行轮次。发布成功需同时满足健康与业务冒烟。
- 证明同一版本重试安全。覆盖错误目标、镜像不存在、迁移失败和坏镜像健康失败。失败退出保留诊断信息和旧镜像，成功路径记录 web/cron 实际镜像与预期一致。

## E2.3 · 自动备份及独立恢复

范围为 `deploy/staging/` 下的备份、恢复、非生产定时入口和使用说明。以 E1.8 的 `pg_dump -Fc` / `pg_restore` 及关键表核对为样例。

- 用显式目标备份 V2 及发布确实依赖的其他数据库，保持分库归档。记录源版本、UTC 时间、库标识、归档校验值和成功状态。只有导出及校验通过的文件可以成为恢复候选。失败产物隔离，错误返回非零并保留脱敏诊断。
- 用合成数据演练定时触发、迁移前备份、保留和恢复。恢复入口只允许本次新建的隔离目标，校验数据库名与连接身份。验证坏归档、目标冲突和失败时保留上一份有效备份。清理仅限本次创建的资源。
- 恢复后核对迁移历史、关键表行数与代表性业务不变量，记录备份与恢复耗时及实际恢复点。生产周期、异地目标、加密、保留、恢复责任人、RPO/RTO 与 OSS 处置列入待决清单。演练测得的数字供批准时参考。

## E2.4 · 迁移前后验证

范围为 `deploy/staging/` 的迁移检查与只读核对 SQL。复用 [演练 SQL](../deploy/rehearsal/README.md) 和现有 Prisma 命令，已应用的迁移历史保持原样。

- 使用连通性预检确认实际 V1/V2 目标。记录迁移历史、预期待应用清单、代表性数据和可恢复备份标识。区分计划内的 pending 与连接错误、失败迁移或非预期历史。
- 对实际镜像分别验证空库和从已知旧 schema 增量升级。迁移后核对两库状态、V2 schema、一致性约束和关键数据。若基线没有真实上一版镜像或迁移样本，记录替代样本的证据边界。
- 注入迁移或核对失败，证明发布流程会阻止后续上线步骤，并保留当前数据库状态用于定位。重跑前先辨认是迁移未执行、迁移失败还是已应用后验证失败。

## E2.5 · 回滚与恢复演练

范围为 `deploy/staging/` 的回滚入口和演练说明。先完成半自动回滚，执行者提供上一版镜像和兼容性证据，再考虑在可证明兼容的情形下自动回滚。

- 演练坏镜像或健康失败。以同一个上一版镜像恢复 web 和 cron，保持数据库已前滚状态。记录回滚前后镜像摘要、schema 兼容证据、健康、核心冒烟与恢复耗时。
- 演练旧应用与新 schema 不兼容时的停止条件。保留现场和写入记录，提交前滚修复或经批准的备份恢复选择。隔离恢复验证受影响数据和停写边界，数据库恢复与镜像回滚分别记录。

## E2.6 · 发布记录与关闭条件

沿用 [E1 发布手册](flower-studio-2.0-release-runbook.md) 的模板。交付 E2 的 staging 操作说明及脱敏证据，必要时更新手册相关段落。记录目标环境、源码 SHA、实际镜像摘要、上一版镜像、审批或执行人、迁移及备份标识、校验、故障决策、恢复时间和资源清理结果。

- 每个工作包提交实际基线、文件范围、执行命令与退出码、通过和失败场景、证据位置、残留风险及知识更新提案。改动后复跑适用的 E1 门禁，并记录结果。
- E2 工程验收要求真实 SHA 镜像在 staging 部署，自动备份可恢复，迁移前后验证可重复，坏版本失败时能停止并按兼容条件回滚，发布记录可复查。仅在本机通过的项目注明环境，远程凭据、目标或仓库设置缺失时记录负责人和待办。
- DSH 自测通过后交 Codex 按 ADR-005 独立复跑及验收。生产放行另由项目用户审批，发布前关闭 PG 卷与版本、生产恢复参数及其他适用的 Runbook 阻塞项。
