# Flower Studio V1 → V2 功能差距矩阵

状态：2026-11-06 首次全量静态盘点。范围包括后台页面、后台 API、通用平台能力及现有小程序 API。第一阶段关闭范围为 WMS 及其必需支撑能力；CMS、CRM 和小程序保留在矩阵中，但安排到后续阶段。本文不以 V2 Schema 中存在模型作为功能已经迁移的证据。

> 2026-11-19 返修更新：A06 与 B02 已补齐 V2 物料/商品/SKU 图片上传、预览和失败占位，状态改为 ✅；D04 的默认 SKU 停用顺序已按 WMS-BR-CAT-001 修复。首段“88 项能力”等统计仍保留 2026-11-06 的原始静态盘点口径；逐项状态以本表当前行为准，验收证据见 `docs/stage-artifacts/sprints/sprint-3-wms-regression-checklist.md`。
>
> 2026-11-19 物料母表补齐：B01 已按 V1 FlowerWiki 迁移拼音简拼、别名、花材角色、多颜色标签、形态、默认可用率/损耗模式、成本更新时间，支持无引用删除与行内改标准成本；B02 的 AI 补全扩展为颜色/形态/供货季/角色/别名建议。物料、供应商、包装方案编号改为系统生成，界面不再手填。约定见 `knowledge/04-Engineering/E0-v2-engineering-conventions.md`。

## 判定规则

| 标记 | 含义 |
|---|---|
| ✅ 已迁移 | V2 已有入口、V2 数据读写及基本业务服务；仍需最终回归 |
| 🟡 部分迁移 | 只有部分入口、字段、操作或异常处理，不能替代 V1 |
| ❌ 未迁移 | V2 没有可用入口或服务 |
| 🔁 新模型替代 | V1 能力不原样复制，但 V2 已有明确替代流程；需做对照验收 |
| ⚪ 待确认 | 是否保留、替代或废弃需要业务确认，确认前不得删除 V1 |

“无缝迁移”要求：V2 入口可发现、数据写入 V2 模型、权限与审计有效、正常和异常流程可完成、页面延续 V1 设计体系、回归通过。仅有数据库模型、测试脚本或只读展示均不算完成。

本轮共识别 88 项能力：10 项已迁移、22 项部分迁移、51 项未迁移、3 项由新模型替代、2 项属于后续非阻断边界。原业务待确认项均已形成迁移决策。“已迁移”仍须在最终 V1/V2 对照回归中验证，不能直接视为上线验收通过。

## J. 明确不应原样迁移的 V1 技术行为

| V1 行为 | V2 处理 |
|---|---|
| `ProductSku.stock` 虚拟库存与物理库存双轨 | 不迁移；由 V2 配方、批次、预留和能力锁定统一计算 |
| 单一订单状态 | 不迁移；由商业、供应、制作、交付四维状态替代 |
| 支付后才执行 FIFO 直接扣库 | 不迁移；V2 在确认/支付节点按入口规则预留，制作时结转实际用量 |
| FlowerWiki、MasterPart 和旧 Material 多套物料身份 | 不迁移；统一为 V2 `Material`，知识资料作为附属信息 |
| 旧 BOM API | 不迁移；统一到 V2 配方版本 |
| 已废弃的旧 Banner API 和旧微信登录重定向 API | 不迁移；只保留规范的新入口 |
| 长期 V1/V2 双写 | 不采用；切换前可对照，正式接管后统一写 V2 |

## 第一阶段范围结论

1. 当前 V2 已实现的主要是核心模型试用闭环，尚不能替代 V1 上线。
2. 第一阶段必须迁移 V1 WMS：物料、库存、批次、仓储、供应商、采购、配方、包装方案、订单履约、WMS 报表及上线运营保障。
3. 商品和 SKU 的基础身份、价格、默认 SKU 与配方关系属于 WMS 运行依赖，第一阶段保留；图片、富文本、运营标签、分类陈列、Banner、推荐位和营销内容属于 CMS，后续迁移。
4. 登录、WMS 角色权限、审计、数据质量和系统健康属于 WMS 上线支撑能力，必须在第一阶段完成；员工管理至少要满足 WMS 账号的创建、停用、重置密码和角色配置。
5. CRM 客户运营以及小程序 API 不阻断第一阶段关闭，可继续使用 V1，后续接入 V2 数据模型。
6. 样品花材搭配属于 V2 新能力，不是 V1 WMS 无缝迁移的阻塞项，仍按已确定的打样阶段实施。

### 第一阶段 WMS 必须完成的矩阵范围

| 范围 | 矩阵编号 | 说明 |
|---|---|---|
| 平台基础 | A01–A08 | 仅围绕 WMS 上线所需账号、权限、Shell、上传、审计和租户门店边界 |
| 物料与库存 | B01–B11 | B12 整卷逐卷状态属于 V2 新能力，不阻断本阶段 |
| 采购与验收 | C01–C10 | 包括当前四项采购试用缺陷和采购分析 |
| 商品/SKU 基础 | D03–D05 | 编号、多个 SKU、价格、默认 SKU、规格和启停；内容运营不在本阶段 |
| 配方与包装 | D09–D11 | 标准配方、版本历史和可复用包装方案 |
| 订单与履约 | E01–E12 | 订单、预留、缺料、制作、支付退款、配送和成本 |
| WMS 运营保障 | H01–H09 | 仪表盘、V1 已有 WMS 报表、上线检查、数据质量和系统健康 |

## 建议迁移批次

| 批次 | 内容 | 关闭条件 |
|---|---|---|
| P0 | 核心模型审计；当前采购缺陷；V1 设计系统与后台 Shell；账号权限 | 数据约束正确，正式导航和权限可用 |
| P1 | 物料、库存、供应商、采购、商品、SKU、配方、订单正式页面 | V1 对应日常业务无需返回旧版 |
| P2 | WMS 仪表盘、既有报表、试运营检查、数据质量、系统健康、审计查询 | WMS 上线运营和排错能力齐备 |
| P3 | WMS 全量回归、性能、备份恢复、部署、真实用户验收和切换 | V2 完整替代 V1 WMS，V1 WMS 只保留短期回退 |
| 后续 CMS | 商品内容、分类陈列、Banner、推荐位、营销、配送设置和图片 | CMS 完全使用 V2 |
| 后续 CRM | 客户、收花人、礼赠和提醒 | CRM 完全使用 V2 |
| 后续小程序 | V1 小程序 API 切换及正式支付增强 | 商品、内容、购物车、下单和用户资料均使用 V2 数据 |

## 已确认迁移决策

1. V1 花材知识库的 AI 补全属于第一阶段 WMS 必须迁移能力。
2. 包装方案维持独立页面和接口，不合并成只能在配方内部使用的功能。
3. Mock 支付在后续小程序迁移时继续保留，但仅允许测试环境启用，生产环境必须禁用。
4. 商品决策建议随 CMS、礼赠推荐随 CRM 迁移；现阶段原样保留 V1 规则，只适配 V2 数据模型，不重新校准算法。
5. V1 中仅用于兼容且已明确废弃的旧 API 在对应模块切换时直接移除，不为 V2 建立兼容实现。

另外两项不阻断第一阶段：整卷耗材逐卷状态按后续门店试用决定启用细节；V1 微信支付回调目前只是占位，后续小程序阶段以正式支付回调替代。
