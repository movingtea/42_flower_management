# Flower Studio 2.0 实施顺序

用户已确认：旧系统没有正式上线，旧连接目标中的数据可以丢弃；不迁移旧业务数据。`deepseek-flower-lab` 是独立 POC，不纳入正式系统，也不改动。

## V1 功能迁移原则

本次重构可以放弃 V1 测试数据和旧表结构，但不能默认放弃已经存在的业务功能。凡是未被 2.0 业务设计明确替代、合并或废弃的 V1 功能，都必须按阶段无缝迁移到 V2，并沿用 V2 的租户、门店、权限、审计和统一业务对象边界。迁移可以复用经过验证的通用组件和纯业务逻辑，但不得让 V2 页面直接依赖旧数据库模型形成长期双轨。

每项 V1 功能必须先进入“保留、V2 重做、合并替代、明确废弃”差距清单；只有完成 V2 入口、数据读写、权限、异常处理和回归验收后，才能移除对应 V1 入口。不能因为某项功能不在当前重构模块中，就把它遗漏在 V1。

各阶段关闭门槛均增加一项：本阶段范围内的 V1 既有功能已经迁移或有经确认的替代方案，不存在只能返回 V1 才能完成的正常业务操作。第一阶段仅要求 V2 完整替代 V1 的 WMS 模块；CMS、CRM 和小程序按后续阶段迁移。

## 第一批：V2 WMS 完整接管与可上线版本

1. 将 v2 Schema 固化为正式初始迁移，建立默认租户、主店和库位；保留租户归属字段与约束，当前只运营一个租户。
2. 完成物料与供应商、采购与分次验收、批次与库存流水、商品与 SKU、配方版本。
3. 完成后台人工订单、确认后物料需求生成、批次预留、缺货与采购需求、制作领用、交付及成本快照。
4. 按已确认的低操作负担原则自动推进正常流程，仅在降级、替代、差异、短缺等例外时要求人工确认。
5. 盘点并迁移全部未被明确替代或废弃的 V1 WMS 功能，使库存、采购、物料、配方、包装、订单履约、损耗、报表及 WMS 运营保障不需要返回 V1 操作。
6. V2 WMS 延续 V1 的整体视觉样式、导航结构、页面密度和主要交互习惯；新业务能力在同一设计体系内扩展，不以当前试用页样式作为正式上线界面。
7. 在空 PostgreSQL 库中完成迁移、seed、权限、并发库存、端到端业务、构建和部署验证，再切换正式后台入口。

第一阶段明确保留 V1 花材知识库 AI 补全；包装方案维持独立页面和接口。已明确废弃、仅用于兼容的旧 API 不迁移。

### 第一阶段结束标志

第一阶段只有同时满足以下条件才算结束：

1. V1 WMS 中未被明确替代、合并或废弃的功能已无缝迁移至 V2，并有功能差距矩阵和回归结果作为证据。
2. V2 WMS 保留 V1 的整体样式与操作习惯，所有第一阶段页面达到可交付给真实用户的正式界面标准，而不是开发试用页。
3. V2 新增的订单、采购、库存、制作、损耗和成本规则通过自动化及真实场景验收。
4. WMS 所需的登录、角色权限、审计、异常提示、数据约束、备份恢复、构建部署和基本性能达到上线要求。
5. 用户可以只使用 V2 完成全部 WMS 正常业务；V1 WMS 仅作为短期回退版本保留。V1 CMS、CRM 和小程序可继续运行，直到各自后续迁移阶段完成。

未满足以上任一项时，第一阶段状态只能是“开发中”或“待上线验收”，不能标记为完成。

## 第二批：打样优化、报表增强与 CMS 迁移

1. 使用统一物料、批次、样品和 SKU 模型完成样品方案、现货约束、拆解复用、实际执行与样品转 SKU。
2. 在第一阶段已迁移的 V1 WMS 报表基础上，补充打样复用等增强报表，统一口径和筛选维度，并核对明细总和。
3. 迁移 V1 CMS 商品内容、分类、Banner、推荐位、场景入口、营销内容和配送设置，并接入 V2 商品、SKU 与库存口径。
4. 商品决策建议原样保留 V1 规则，仅适配 V2 数据模型。
5. 这批完成并通过真实花店场景试用后再启动 CRM 和小程序接入。

## 第三批：CRM 与小程序接入

迁移 V1 CRM 客户、收花人、礼赠和提醒能力，礼赠推荐原样保留 V1 规则；接入小程序商品展示、SKU 选择、购物车、下单与支付、短时能力锁定、支付回调、订单进度与配送。保留后台人工下单入口。Mock 支付仅保留在测试环境，生产环境禁用。
